# OCS Godot 项目约束

2026-11-27 · 适用于 `OCS_EASTERN` 的原生 Godot 实现和后续作品接入。

以 Godot 4.7 标准版和 GDScript 为运行基线，当前验证版本为 4.7.2。《第三冬》作为首个作品，实现 OCS v4.3 通规、作品专规、剧本规则三层模块化。同一套引擎供 Windows 客户端、后续 Android 客户端、联机裁判和 Linux 无头模拟使用。先完成《第三冬》和后续各单作品，再接入联合剧本。当前 08 地图仍走 Node 桥接，现有 TypeScript 引擎保留为迁移对照和开发期数据工具。具体移植顺序见[全 GDScript 迁移方案](../games/third-winter/docs/2026-11-27-核心算法全GDScript迁移方案与Unity对比.md)。

工程结构、作品包接入、会话接口和阶段验收见 [Godot 纯 GDScript 架构方案](Godot纯GDScript架构方案.md)。

## 1. 规则归属与覆盖顺序

| 层 | 负责什么 | 接入示例 |
| --- | --- | --- |
| **OCS 通规** `scripts/rules/series/` | 接收中立规则事实，提供通用判定、计算和流程。 | 地面移动、ZOC、补给搜索、战斗与骰序所需的通用判定。 |
| **作品专规** `works/<work_id>/rules/` | 在通规结论上应用作品级条件和例外，提供本作需要的规则能力。 | 第三冬姿态、RVGK、Kessel 和作品天气表。 |
| **剧本规则** `works/<work_id>/scenarios/<scenario_id>/` | 声明初设、可用地图、增援、日期、胜利条件，施加该剧本独有的覆盖。 | 08 的专用天气与初设窗口，09 的地图裁切与剧本配置。 |

- 适用时，优先级为 **剧本规则 > 作品专规 > OCS 通规**。默认判定由通规给出，作品与剧本按规则条款修正。静态差异用数据表达，需要计算的例外用明确的能力接口或回调表达。
- 按移动、补给、战斗等机制组织实现，每个机制有统一的合法性判定和状态写入入口。作品和剧本覆盖具体判定及其适用窗口，其余判定沿用该机制的默认行为。开局装配该局适用的能力，预演、正式提交和控制器查询共用判定。
- 引用方向为剧本 → 所属作品 → 通规。共享层只接收中立数据与接口。作品之间保持独立，第三冬专有格号、单位、国籍限制和阶段例外留在所属作品或剧本。
- 每个机制登记规则版本、条款、触发窗口、行动方、输入和状态写入。涉及高层覆盖时，记录覆盖点及来源。已有机制优先复用，规则修订与等价移植分别验证。 [仓库开发规范](../AGENTS.md) · [规则三层分工与优先级](../games/third-winter/docs/2026-11-26-规则三层分工与优先级.md)

### 条款注释格式

规则代码中的条款号要带来源缩写，标在实际执行判定的函数或分支附近。`TTW` 是《第三冬》的作品缩写，后续作品接入时登记各自的缩写并统一使用。

| 来源 | 写法 | 示例 |
| --- | --- | --- |
| OCS 系列通规 | `OCS v<版本> §<条款>` | `OCS v4.3 §6.1d` |
| 作品专规 | `<作品缩写> SR §<条款>`，`SR` 表示 Specific Rules | `TTW SR §3.5b` |
| 剧本规则 | `<作品缩写> S<剧本号> §<条款>`，无编号时用印刷页码 | `TTW S08 pp.54–56` |

- 默认判定和覆盖分支分别标注自己的出处。一个判定确实同时用到多个来源时逐一注明，便于核对覆盖关系。
- 作品包登记适用的专规和剧本册版本。多版并存时，在注释中补充用于实现的版本或发布日期。项目裁定按日期与记录引用，代码移植参考单独注明。
- 无编号条目可标印刷页码、表名或条目名。测试和开发诊断需要报告规则来源时，使用相同的缩写与编号。

## 2. Godot 工程与依赖边界

共用一份 Godot 项目和共享规则源码。08 迁移先在现有 `games/third-winter/godot/` 内按下列 `res://` 布局开发。接入第二个作品前，将现有工程整体移至仓库根的 `godot/`，并在独立改动中验证启动、资源与导出路径。各作品可以配置各自的发行包。

```text
res://
  scripts/
    core/              # 中立状态类型、命令信封、回执、确定性随机数
    rules/series/      # OCS v4.3 通规
    match/             # 对局状态、命令分派、阶段与待决应答
    view/              # 按观察席位投影视图和可用动作
    data/              # 运行数据读取、归一化、校验和指纹
    session/           # 会话装配、席位权限、串行提交、存档和恢复
    controllers/       # 人类、远程客户端与外部 AI 的命令适配
    ui/                # 菜单、地图、辅助卡和交互草稿
    headless/          # Linux 无头裁判与模拟入口
  works/
    third-winter/
      rules/
      scenarios/
      assets/
  tests/               # 无头回归、规则夹具与跨实现对照用例
```

- `core`、通规、专规、剧本规则、`match` 和 `view` 可用 `RefCounted` 或纯数据脱离场景树运行。文件读取和 JSON 解析在数据或会话边界完成。场景节点、帧率、系统时间、输入设备和全局可变单例只属于外围代码。
- `match` 依赖中立契约，由会话注入作品规则和剧本数据。依赖从 UI 与会话流向 `match` 和 `view`，再流向已声明的规则能力。`match` 与规则层不引用 `view`。`view` 读取对局状态与规则查询，生成按席位过滤的投影。UI 读取投影、维护本地草稿并提交命令。棋盘、辅助卡、库存和回合轨从同一对局状态派生。
- 新作品通过注册 `workId` 和所属 `scenarioId` 接入。每个剧本提供适用规则版本、初设、地图、数据版本及所需规则能力。普通剧本装配单个作品包，装配边界为后续联合剧本保留多个作品包的入口。缺少必需数据或能力时，开局明确报错。新增作品的代码落在其作品目录和装配注册处，共享层新增内容须有 OCS 通规依据或中立能力需求。

## 3. 对局、投影与持久化契约

- 同一会话入口处理 `submit(seat, command)`、`project(viewer)` 和只读的合法动作查询。命令沿用 `{id, expectedRevision, action}`，由 `action.type` 区分动作。席位身份由会话确定，拒绝结果提供稳定错误码和可见提示。GDScript 公开方法标注参数和返回类型，函数和变量用 `snake_case`，外部协议和旧档字段保留原有大小写。
- 会话区分**阵营、席位、阶段所属方、当前行动或应答方、观察席位**。跨方应答保存当前责任方、所在步骤和返回位置。行动权限同时检查席位、控制范围和当前窗口。公开事件、错误消息和各席位投影均遵循相同的可见性规则。
- 每局串行提交。已接受的同一席位、同一 `id` 重试返回原回执修订号，即使命令携带的修订已过期。新命令检查修订、错方、越序和目标资格。提交成功后统一发布新状态、修订和回执。批量命令若按一项操作提交，整批结算成功才生效。预演与结算使用已隔离的候选状态，避免 GDScript 容器的共享引用使拒绝路径改写盘面或骰序。
- 对局随机使用确定性 `mulberry32`，持久化 `seed`、`state`、`drawCount`。相同规则版本、数据指纹、初始条件、种子及命令序列须产生等价结果。参与规则判定的遍历顺序、平局处理和搜索选路须显式确定，便于 Windows、Android 和 Linux 回放相同命令。
- 存档保存作品、剧本、规则和数据版本、数据指纹、权威状态、待决应答、修订、回执及随机状态。需要续局的正式对局先完成原子持久化再确认成功，写入失败保留上一份有效记录。同一存档仅有一个写入者。训练模拟可只在内存中提交，由调用方保存可复现的种子和命令序列。新格式与旧 08 档分别做恢复测试，支持旧版时通过明确的读取或迁移路径处理原档。 [现有回执语义](../packages/match-core/src/command-log.ts) · [08 存档实现](../games/third-winter/desktop/local/store.mjs)

## 4. 游戏模式与席位

模式由席位、控制者、可控范围和连接方式组成，各模式共用规则、待决应答和投影。多人共控一方时，房间明确每个席位可操作的单位、编制或共享决策。同一应答窗口的冲突由权威会话按席位权限与修订处理。

| 模式 | 沿用 ID | 席位配置 | 目标入口 |
| --- | --- | --- | --- |
| **单人 SOLO** | `solo` | 一名玩家在本机轮流控制双方，跨方应答时切换操控席位。 | 本地会话 |
| **双人 PVP** | `pvp` | 两名玩家各控制一方。 | 联机房间与权威裁判 |
| **多人 PVP** | `pvp-multi` | 双方均可分配多个玩家席位，至少一方由多名玩家协作。控制范围按剧本和房间分配。 | 联机房间与多席位权威裁判 |
| **单人 PVE** | `pve` | 一名玩家控制一方，外部 AI 控制对手。 | 本地会话与 AI 控制器 |
| **多人 PVE** | `pve-online` | 多名玩家协作控制同一阵营的席位，外部 AI 控制对手。 | 联机房间、权威裁判与 AI 控制器 |

五种模式均为交付目标。多人 PVP 的房间在开局前固定席位、控制范围、共享决策责任及跨方应答的认领规则。涉及全阵营的动作由配置中有权的席位提交。同一阵营的多个玩家可以同时查看各自局面，命令仍按修订串行结算。联机客户端发送命令并接收该席位的投影与回执。裁判负责席位映射、规则、骰序和持久化，重连从权威修订恢复，并重新投影当前待答方与合法操作。只有模式、剧本和所需控制器都已接通时，菜单才允许开局。 [现有模式定义](../games/third-winter/godot/scripts/menu.gd)

## 5. 外部 AI 与 Linux 无头训练

项目交付可替换的 **AI 控制器接口、Linux 无头模拟入口、接口说明和可重复的联调样例**。第三方负责 PVE 策略、训练框架、奖励定义、模型权重和模型托管。项目以固定命令序列的测试控制器验收接口。游戏和规则引擎仅使用 Godot/GDScript 运行，第三方可自行选择外部进程的实现语言和训练工具。

| 接口能力 | 契约 |
| --- | --- |
| `describe` | 返回接口版本、作品和剧本 ID、规则版本、数据指纹及支持的能力。协议版本或数据不符时给出可识别错误。 |
| `reset` | 仅供受控模拟入口调用。按作品、剧本、明确种子和初设选择创建独立新局，返回起始修订。线上或正式 PVE 客户端没有重置、指定骰点或读取 RNG 内部状态的权限。 |
| `observe` | 按已分配席位返回当前修订、阶段、待答方及该席位可见的结构化盘面。观测依赖稳定实体 ID 和格号。 |
| `legal_actions` | 在当前修订下提供合法动作与参数约束。路径、多单位选择等组合操作可逐步查询候选和预演，校验沿用正式命令入口。 |
| `step` | 提交正常对局命令，返回接受或拒绝、修订和可见事件。结果区分继续、待答和终局，终局提供规则认定的结果与可见计分。 |

- 正式 PVE 的 AI 和人类共用权限。无头自对弈可由外部程序受控地给双方分配控制器，各控制器各自读取本席位观测。外部程序以动作驱动模拟，选择并行进程数和采样方式，按需记录命令和回合结果。
- 协议字段独立于中文文案、菜单临时键、像素坐标和贴图。正式 PVE 若遇超时、断连或非法命令，保持当前应答窗口，返回可处理错误，允许重连、重试或按对局配置交由有权玩家接管。
- Linux 无头入口直接装配同一套 GDScript 对局会话，可在无窗口和无图像资源的环境运行。首个进程适配可采用版本化的逐行 JSON，请求与响应通过请求 ID 匹配，诊断日志与协议数据分流。对外发布训练接口时提供启动命令、协议样例及一个固定种子的 `reset → observe → legal_actions → step` 流程。 [Godot 4.7 命令行](https://docs.godotengine.org/en/4.7/tutorials/editor/command_line_tutorial.html) · [Godot 4.7 专用服务器导出](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_dedicated_servers.html)

## 6. LLM 指挥 API

AI 控制器预留可选的 LLM 指挥适配器。接入链路为 **席位观测 → LLM 指挥建议 → AI 控制器选取合法动作 → 权威会话结算**。LLM 负责提出游戏内目标和优先级。AI 控制器负责把建议落实为可提交的动作，并在提交前按当前修订重新校验。

| 契约 | 要求 |
| --- | --- |
| 指挥请求 | 版本化 API 提供请求 ID、席位、局面修订、阶段、该席位可见的盘面摘要及可选目标。盘面和日志中的文本按数据传递。 |
| 指挥响应 | 返回关联的请求 ID、对应修订、目标或任务 ID、优先级及可选的单位或格号。控制器校验 JSON 结构、目标范围和当前行动窗口。 |
| 连接与权限 | 模型服务由会话外围的适配器调用，允许更换本机或远程提供方。服务密钥由运行环境管理。适配器只获得当前席位的投影和查询能力，正式落子通过同一个 `submit`。 |
| 失败与回放 | 超时、断连、格式错误或过期响应保留当前窗口，允许重试、切换已配置控制器或由有权限的玩家接管。回放记录最终接受的对局命令，从固定种子复现结算。 |

供应商 SDK、模型进程和训练框架由外部适配器选择。Godot 规则不等待模型网络请求，Linux 无头测试可用固定响应替身验证指挥链路。

## 7. 联合剧本接入

- 项目方已处理联合剧本的地图和剧本数据。**《第三冬》和后续各单作品全部实现并通过各自验收后，才开始联合剧本接入。** 单作品阶段实现共用机制、独立作品包和剧本装配边界。
- 联合剧本在独立的装配描述中引用参与作品及其数据版本，复用已有单作品规则与数据。按作品和地图辨别同号格及同号算子，再按已处理的数据映射地图接缝和重叠格。盘面使用唯一的规则格与实体 ID。装配描述同时明确跨图邻接、初设、增援、回合及胜负条件。
- 每条作品专规按联合剧本指定的地图区域、单位归属或规则窗口生效。同一判定出现重叠覆盖时，由联合剧本明确适用条款。无法确定归属的格、算子或规则冲突在装配时报告。联合作战规则仍走共享会话的合法性、命令、视图和存档契约。

## 8. Android 客户端

Android 是后续客户端交付目标。与 Windows 客户端共用 GDScript 规则、剧本数据、会话、命令和存档格式。平台差异集中在输入、界面布局、应用生命周期和打包。联机模式使用同一裁判协议与席位投影，Linux 无头训练和外部 AI/LLM 服务继续通过控制器接口接入。

- **输入与布局**。鼠标和触屏输入在 UI 层转换为同一操作。触屏须能选格和选子、查看叠堆、打开动作菜单、平移缩放和确认落子。为依赖右键、悬停或双击的操作提供触屏入口，区分缩放、拖拽和落子。菜单、侧栏与地图按可用视口布局，适配手机和平板的屏幕比例及安全区域。 [Godot 触屏输入](https://docs.godotengine.org/en/4.7/classes/class_inputeventscreentouch.html) · [多分辨率布局](https://docs.godotengine.org/en/4.7/tutorials/rendering/multiple_resolutions.html)
- **资源与运行**。移动端使用包内 `res://` 资源和应用私有的 `user://` 存储。本地对局由 Godot 原生会话运行，资源定位使用可随包分发的路径。规则格网与地图贴图分开，移动端贴图可按真机内存与性能调整，格号、可见信息和规则判定保持一致。 [Godot Android 导出](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_android.html)
- **挂起与恢复**。应用切到后台、系统终止或网络切换后，本机对局从最近的已提交修订恢复，联机对局从裁判端重新同步。待决应答、骰序和回执随权威记录恢复，重试沿用原命令 ID。

## 9. 数据、导出与验收

- 发布所需规则数据按版本存放在 `res://`，存档和运行配置写入 `user://`。数据装配验证必需字段、数值类型、单位与格号引用、地图边、初设和增援。修订号、骰面、库存等整数在 JSON 边界校验范围后转换，缺字段与显式空值分别处理。规则格网与像素标定独立，规则状态采用稳定 ID 与可序列化类型。数据导入可在构建前执行。
- Windows 和 Android 客户端导出带齐运行数据、贴图和字体。Linux 裁判与模拟发行物带齐相同版本的规则和数据，客户端专用素材可省略。导出配置显式包含运行期读取的 JSON，并检查 PCK 文件名大小写与实际资源引用。 [Godot 4.7 导出说明](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_projects.html)

| 变更范围 | 验收条件 |
