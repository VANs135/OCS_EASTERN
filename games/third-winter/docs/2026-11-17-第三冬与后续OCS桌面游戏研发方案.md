# 第三冬与后续 OCS 作品桌面游戏研发方案

2026-11-17

## 1. 交付形态与研发路线

第三冬首版交付可独立安装的 **Windows 桌面游戏**，并支持 **互联网双人联机**。两名玩家可以在不同地点通过邀请加入同一局，从初设打到终局，关闭程序后也可以回到原阵营继续。保留本地双人同机模式，供离线推演和规则回归。

首发按 **Windows x64、好友私房 1 对 1、可跨会话续局** 规划。正式客户端由开始菜单启动，包含窗口、菜单、键鼠与高 DPI 支持、系统文件对话框、版本更新与可诊断的错误提示。地图和算子等资源随安装包在本机加载。由一处公网服务托管线上对局，玩家双方通过出站连接加入。

**建议先用 Tauri 2 客户端配独立 TypeScript 裁判服务打通一局，同时用 Godot 4 做同场景对照。** 先确定一套与客户端技术无关的对局协议。即便以后换用 Godot，仍可复用服务器上的通规与第三冬专规。首个正式联机剧本定为已有初设资料的 Scorpion（剧本 8）。

从斯摩棱斯克已核对的 **`23262ec96b8f`** 建立独立研发线。当前作品继续做 UI 与操作优化。以后，一般性的规则修复、地图交互和桌面能力通过可单独回归的小批变更回流。等两个作品都通过共享接口和回归测试，再稳定共享包的发布接口，供下一作接入。

## 3. 通规、作品与剧本如何接起来

| 层 | 职责 | 实现形式 |
|---|---|---|
| 系列通规 v4.3 | 通用阶段骨架、模式、RE、ZOC、移动、战斗、补给、空军及确定性掷骰 | 共享 TypeScript 内核，接显式规则表、地图拓扑、单位和当前局面 |
| 作品专规 | TTW 的地形表、增援和天气表，以及本作新增的行为和触发点 | 游戏资料包提供表与参数。小型规则模块提供有状态或改变时机的专有机制 |
| 剧本 | 有效地图、起止日期、部署、轨距与铁路端点、部队与离图盒、首回合天气、增援、胜利与明确例外 | 单剧本数据和需明确指定的覆盖。对缺少的初始数据报错并指出来源位置 |

规则生效顺序为**剧本 > 作品专规 > 系列通规**。表格和数值按字段做有定义的覆盖。需要玩家选择、经过多个阶段或更新盘面状态的规则用独立模块表达，按现有场景接点逐步增加接口。例如，在首个苏军战斗单位移动进入指定桥端格时，第三冬把桥破坏的选择交给轴心。结算或放弃后回到同一移动过程，重复提交同一动作只能结算一次，存读档也须保存当时的选择和继续点。

阶段用既有的**节 / 环 / 块**组织，再为每条专规记录「谁、什么时机、做什么、在哪里」。规则触发需区分「主玩家」「行动玩家」「响应玩家」。自动结算由内核执行，界面呈现结果和来源。补给等支付只以最终结算为准，预览不得修改局面或消耗随机数。把原文账、实现账和用户裁定账分别维护。专规行为与规则数值取自第三冬专规、对应剧本、辅助表和已确认的第三冬裁定。凡数据包仍欠的条目，导入报告注明缺项和来源，规则用例按来源验证。 [第三冬专规梳理](<D:/war game/OCS各作数据库/OCS第三个冬天/docs/2026-11-11-第三冬专规梳理.md>)

扩编时只为实证需求增加接口，例如「移动中断并请另一方响应」「阶段首尾处理」「地图连接分类」。每个接口同时用通规基线、斯摩棱斯克回归和第三冬专规用例验证。后续作品按相同入口导入资料和注册自身机制，先以一个真实剧本验证再扩面。

**联网接点。** 现有 `src/engine/session.ts` 已按问题 ID 和应答方检查响应，`src/engine/rules/fog.ts` 有可见单位及骰面可见性判定，`src/engine/log-book.ts` 可核对随机序列。当前会话和盘面仍分开保存，先将一条实际对局链路的盘面、台账、决策和恢复点收敛到同一规则状态，再将 Pinia 中直接更新局面的操作改为调用统一命令入口。线上服务从席位凭据确定阵营，使用同一入口做权威校验与提交。本地模式在机内调用同一规则内核。回放复用现有随机与日志测试思想，正式线上裁判保存服务端抽取和动作顺序，用记录的结果驱动回放。 [待决与结算](<D:/OCS/smolensk/src/engine/session.ts>) · [战争迷雾](<D:/OCS/smolensk/src/engine/rules/fog.ts>) · [日志与回放](<D:/OCS/smolensk/src/engine/log-book.ts>)

## 4. 第三冬数据库怎么接

### 4.1 战役地图与小剧本地图

新版 `地图数据库` 是战役地图的输入。已读到 `map_hexes.json` 的 **8,928 条源格记录**和 `map_edges.json` 的 **27,564 条源边记录**。其中有 186 条半格记录、248 对标注的接缝双记录，以及 1,417 条空端点边界或接缝记录。源记录数量用于导入核对，可玩格和内部边数量由拓扑校验后给出。旧 `data/terrain_hexes.json` 与 `terrain_hexsides.json` 标为 Scorpion，用于该小图的独立导入和回归。

1. 固定校准成果版本。源 JSON、原图和裁定字段只读，生成经过校验的运行包。保留原始 ID、印刷格号、拼合位置、有效范围和来源。比如把 `D14.03` 与库中的 `D14.3` 解析为同一格，并保留可回读的印刷写法。
2. 核对 `seam_twin`、`seam_primary` 和格边接缝字段，保证每个实格及实边在寻路和叠堆中只出现一次。空端点边按合法图缘接口、拼合接缝残段或异常分类。内部边要求两端存在、邻接互反。保留校准字段和已确认的人工结果，对仍标待视检的分类按首批剧本及专规关键位置抽查。当前发现 11 组接缝双记录的道路或铁路等级不一致，其中 10 组涉及单双轨，须保留两侧证据定值。接缝主标记只用于确定主记录。
3. 静态底图记录地形集合、城镇等级、道路、小路、铁路单双轨、河流、桥及设施。剧本建立初始轨距、控制、桥况、设施和入口，随后由对局状态更新。现有 `printed_facility` 为空的格需要核对图例和场景资料再补 POI、港口等设施，空值不用于判定设施不存在。大图以 A–D 同一拓扑运行，Scorpion 用 `s` 格号和独立地图标识。只有核实过的地理对应才可建立映射。
4. 先对三类位置做验收。**Kherson** 用 D14.03↔D15.03 做 Transport 与 trace supply 的特例连通，河岸仍按 Volga-Class 处理战斗。**补给源**用 2.1a／3.1a 分别核对 A 图北缘与 D 图南缘的道路、铁路和适用日期。**VP 地形**用现有 Kiev 城市组候选 B3.24、B4.23、B4.24、B5.24、B6.23 对照原图，并核指定第聂伯河河段两岸格。结果进入规则数据，带原图格号和条款，可回填原梳理的 Q03、Q11。

### 4.2 单位、算子、初设与到达

`data/README.md` 所列八份结构化单位／标记表合计 **1,558 条定义记录**，其中地面表 1,248、HQ 76、航空单位 43、标记 102。另有 `units.json` 内 **1,640 条 VASSAL 图档/条目记录**。两份编成件明细 `units_axis_fmt.json`、`units_sov_fmt.json` 共 540 条，其正面图已在地面表出现。检查还发现三组旧 ID 冲突和 42 个空标记 ID。导入时应逐字段合并证据，避免把同一物理算子重复入库。

1. **建立角色与身份。** 定义地面单位、空军、HQ、交通点、编成牌和标记的类型与必填字段。以第三冬稳定 ID 关联印刷身份、正反面、图片、原 ID 与别名。实际在盘上的算子实例、库存份数及其状态独立于定义。不同副本可以引用同一单位定义和图片。
2. **先导入校准过的结构化表。** 以 `units_inf_div.json`、专门的 HQ、空军、交通、编成和标记表作为候选。处理顶层与嵌在正面里的 `back`、数值字符串、括号防御值、RE 分数、机动类型和军别。编成件明细与 VASSAL 图档补核身份、图像和冲突字段。OCR、备份、预览表保留为证据。面值的推断标记随来源保留，优先核对首个剧本实际使用的字段。冲突行进入核对报告，按已确认的校准记录、算子印面、官方到达表及条款逐字段解决。缺值保持待核状态。
3. **验证引用。** 正反面图像、父编成、方面军色条、类型能力、RVGK/Alert 等离图池、初设与撤编目标须能解析。旧名字只作输入别名。禁飞、放置资格、军种组合与供给限制由规则层判断，单位库记录类型、参数和归属。
4. **先跑已有剧本输入。** `data/scenarios/08-scorpion` 是所给 `data` 目录内已经分出的正式剧本包，含初设、增援和胜负。已有旧名称引用可以解析到结构化表，导入时再逐项核对格号有效性、重复副本和缺失印值。相邻 `TTBDATA NEW` 中的剧本、OOA 与图表 JSON 可作为后续导入候选，按本作 PDF 和校准记录定稿后再用。

## 6. 互联网联机怎么做

### 6.1 玩家流程与裁判职责

1. 一方在桌面客户端创建私房，选择剧本，发邀请码。另一方加入后，两人确认阵营和版本。首版通过独立席位凭据识别玩家，一次性入席邀请与续局凭据各自管理，支持退出后重连及换设备恢复。创建及加入走 HTTPS，对局动作和更新走加密 WebSocket。
2. 客户端发送行动意图，例如「某单位沿这条路径移动」「回应当前是否炸桥」。命令带唯一 ID、预期状态版本和待决问题 ID。服务以认证席位和当前局面校验归属、时机、行动资格和费用，由服务端执行掷骰、查表、变更局面和提交日志。
3. 每个房间按顺序处理命令。有效命令的状态、动作结果、随机结果和去重记录在同一次持久化提交中保存。命令先查去重记录，再对尚未处理的命令核对状态版本。提交后才确认和广播。重复提交返回先前结果，避免断线重试导致重复掷骰或扣补给。版本落后的操作提示先同步，再由玩家重新决定。
4. 服务按阵营生成可见数据。盘面、堆叠、离图盒、私有骰、日志、可行动作和错误提示使用同一套可见性规则。按席位列出允许发送的字段，客户端收到的是本席位可见的结果或快照。线上掷骰用服务端安全随机源，将已结算的骰面与动作一起保存，用于按序重放和验算。后续骰序与完整后台状态留在服务端。
5. 断线后回到同一席位，取得可见快照或遗漏的更新，并恢复原来的待决问题。服务重启后也必须能从最后提交恢复。比如轴心在苏军移动中待选是否炸桥，断线前未提交就继续等待，已提交但确认丢失就恢复对应结果。用户关掉桌面客户端后仍可在以后的会话续局。

### 6.2 首版部署与数据版本

- 建议先从一套独立运行的 **Node.js／TypeScript 裁判服务**开始，公网 HTTPS／WSS 入口加持久数据卷。入口限制试码与请求速率，记录房间恢复失败及服务状态，便于维护。首版可用 SQLite 保存房间、席位、动作和快照，配定期备份及恢复演练。地图与算子静态资源留在客户端。服务加载与结算有关的规则、地形拓扑和剧本包。
- 房间固定作品、剧本、协议、规则及资料版本。创建和加入时校验，客户端不兼容时提示所需版本。发布更新前验证已有房间仍能打开，活跃房间沿用其建立时的规则和资料版本，迁移须有版本测试和可恢复备份。
- 线上进度由房间管理。玩家可从「继续联机对局」回到席位，并查看自己的可见战报。本地热坐继续使用按作品独立的文件存档、自动存档和上一可恢复版本。桌面文件服务沿用现有序列化设计，存档读入时先校验版本及引用，再恢复局面。

### 6.3 首版联机验收

| 验收项 | 必须演示的场景 |
|---|---|
| 公网对局 | 两台 Windows 机器分别使用两个外部网络，从安装、创建房间、邀请、认领阵营、初设到剧本终局。玩家机器无需开放入站端口。 |
| 即时响应 | 苏军移动触发轴心选择，由正确席位响应后回到原动作。用第三冬 1.4a 的主图测试局验证炸桥，另用剧本 8 验证正式流程。 |
| 长局续玩 | 分别在待决、提交前、服务已提交但客户端未收到确认时断网，验证重连。关闭两个客户端和重启服务后，仍能回到正确回合与动作。 |
| 权限与一致性 | 用两个席位抓取各自实际收到的消息，检查敌方隐藏堆叠、离图盒和私有骰。验证错误席位不能应答，重复命令只结算一次，旧版与资料不匹配的客户端有明确反馈。 |
| 桌面交付 | 干净系统安装与卸载、开始菜单启动、窗口和高 DPI、地图查看与搜索、本地存档导入导出。离线热坐、联机恢复分开验收，在 A–D 战役图实测性能。 |
