# 第三冬规则引擎模块化方案

本方案用于推进全景剧本，并为后续桌面 UI 和其他 OCS 作品保留稳定接点。现有瓶中蝎是每批改动的回归基线。当前代码已将后勤、地面战斗、空军和射击归到各自的命令模块。以下标为目标的分层随实际机制逐步落地。

全回合各阶段及第三冬专规的具体接入时点见[全回合流程矩阵](2026-11-21-全回合流程矩阵.md)。

## 1. 回合定时机，机制负责结算

用「节 / 环 / 块」标定每项行为。**节**是回合或玩家阶段，**环**是该阶段的行动或应答窗口，**块**完成一条可以单独核对的规则动作。每个块登记「谁 / 何时 / 做什么 / 在哪里」。自动结算也有块，归属触发它的窗口。实现文件按有独立规则和状态的机制划分，一项机制可以由多个环调用。

| 节 | 环 | 块及责任模块 |
| --- | --- | --- |
| 回合开始、玩家阶段切换 | 天气、先手、阶段结束检查 | 阶段流程拥有回合及阶段游标。瓶中蝎的解冻流程负责剧本例外 |
| 整备、增援 | 飞机整备、计划到达、可变补给、替换与重建 | 空军模块结算整备，增援模块管理到达义务，单位库存模块负责重建时的实体身份 |
| 移动、反应、扩张 | 地面移动、运输、工程、突袭及各自允许的射击窗口 | 移动负责路线和移动力，后勤负责补给支付、运输与工程，战斗负责突袭，射击负责炮击、轰炸和低空扫射的解算与目标限制 |
| 补给 | 追溯、具象补给、部队储备、断补损耗 | 后勤拥有支付与追溯，损耗块核对选中的算子和实际减员 |
| 战斗 | 宣告、守方应答、查表、损失、撤退、推进 | 地面战斗模块拥有待决战斗。突袭复用战果和撤退路径。进入新格调用同一套进格与占据结算 |
| 整理 | 清除到期状态、库存返回、回合结束判定 | 阶段流程依次调用有明确时点的块。以后接入的战役改轨由铁路模块读取整理阶段开始时的快照 |

上表是代码分工图。每条规则的具体合法时机依原文和已确认裁定登记。跨阶段调用示例为「突袭」发生在相应移动窗口，战斗模块负责结算，移动模块负责后续合法移动。空军任务暂停等待对方拦截时，会话阻止其他不相容操作，空军模块负责应答内容。

### 地面战斗应答的顺序

斯摩棱斯克《阶段 / 环节 × 操作矩阵》的阶段、环节及触发方式可作为记录格式参考。它在 F 段将战斗宣告和结算合列为一个环节，也记录了部分已挪到初设的操作。第三冬在战斗环内展开有顺序的应答，用 OCS v4.3 §9.2（原版 PDF 第 14 页）及 §9.10–9.12（第 17–18 页）逐项定位。

| 原文落点 | 当前操作与时机 | 引擎处理 |
| --- | --- | --- |
| §9.2 第 1–2 步 | 攻方选择攻击格、目标格并支付攻击补给。守方接着决定守方战斗补给 | 宣告成功后打开 `defender-supply` |
| §9.2 第 3 步 | 攻方先选行动值单位，再由守方选择 | `attacker-rating` → `defender-rating` |
| §9.2 第 4–7 步 | 守方对目标格及各攻击方向选择合法地形。之后按顺序自动确定初始攻防比、DRM、奇袭与战斗结果 | `defender-terrain` 触发计算和骰点。符合本作重掷条件时，先完成相应骰点的重掷应答，再继续原步骤 |
| §9.2 第 8 步、§9.10b–c、§9.11c、§9.12 | 攻方完全执行战果后，守方才决定自己的战果。双方先结算强制损失，再处理选项。需撤退时由所属方完成路线 | `attacker-result` → `defender-result`。撤退若中断，在该方的 `retreat` 窗口继续。战果校验包含行动值单位优先承担第一步损失 |
| §9.2 第 9 步、§9.12g | 目标格空出且攻方未撤退时，合格攻方处理战后推进 | 正规战斗开放 `advance`；突袭的强制进格与后续移动由突袭模块结算 |

第三冬会话按当前应答拒绝越序命令及另一方提交。桌面从同一个描述读取行动方、下一条命令和目标格。上述顺序属于通规记录，瓶中蝎重掷和自动夺取按各自来源归到实现或本作裁定记录。

## 2. 代码所有权与依赖

| 层 | 职责与代码入口 |
| --- | --- |
| OCS v4.3 通规 | `packages/series` 放已确认可共用的阶段顺序、查表、移动与运力计算等。通过参数接收局面、地图和规则表 |
| 第三冬专规 | `src/ttw` 保存本作规则的判定。本作特例明确指定作用的规则及窗口。斯摩棱斯克专规、数据和裁定独立保留 |
| 剧本资料 | `src/import` 及剧本装配代码读取和校验地图、单位、剧本初设、增援和表格。瓶中蝎与全景剧本分别装配数据和明确的剧本特例 |
| 对局会话 | `scorpion-session.ts` 统一接收命令，管理待决应答、掷骰及回执，分派到相应模块。正式写入经过这一个入口 |
| 机制结算 | `src/match` 的机制模块负责合法性、费用和状态变化。后勤用 `scorpion-logistics-actions.ts`，战斗用 `scorpion-combat-actions.ts`，空军任务和射击分别用 `scorpion-air-actions.ts` 和 `scorpion-fire-actions.ts`。空军任务等待射击应答，射击结束后交还空军流程处理返航 |
| 界面投影 | `src/view` 和桌面控制器生成合法操作、待答、轨道、盒库存与算子位置。界面提交选项并从新局面重绘。后续 Unity 或 Godot 可沿用 [桌面 UI 契约](2026-11-20-瓶中蝎桌面UI接口.md) |

在新代码里明确每一类状态的更新者。补给支付统一通过后勤账，地图位置由移动、入场或撤退块提交，并统一触发进格规则。算子定义、实例 ID 和所处盒或地图格分别记录。标记的数量、到期和位置由规则状态生成投影，更新一次对局后同步刷新地图和辅助卡。

`packages/series/src/supply-network.ts` 由瓶中蝎现有实现提取。它处理 OCS §12.3、§12.6–12.7 的直接拖取、HQ 投送、轨道与延补队连通。`campaign-ground-position.ts` 从当前算子和有效模式生成占格与敌方 ZOC。`createCampaignBreakoutBoard` 把合法地图区域、规范化格号、移动与追溯成本、共享补给网接到突围查询与命令。其 `inTrace` 输入普通追溯候选，由作品规则结合编队、指挥和特殊来源判定有效抽象补给。首次失去追溯的历史由补给状态提供。缺少所需事实时相应突围不可执行。正式地形、跨图距离、补给源和专规权限仍须装配。

通规按既有模块迁移。先在 `packages/series` 查找可调用代码，再从斯摩棱斯克提取经核实的实现与用例。瓶中蝎已复用射击时机、普通玩家回合流转和补给义务。阶段换边由 `turn.ts` 处理，补给阶段由 `supply-progress.ts` 给出部队储备恢复、供给确认、待分配损耗和结束顺序。瓶中蝎继续按本作规则生成追溯、供给和骰点。全景接入时，可从 `sop-segments.ts` 提取通规窗口，从 `trace-supply.ts` 提取共用判定，从 `breakout.ts` 提取突围规则。瓶中蝎按剧本册第 53 页跳过突围。全景使用第三冬的返场条件。斯摩棱斯克当前工作分支继续使用自己的接口，待它接入共享包时再统一调用源。

命令入口按明确的命令类型分派。新增命令若漏接，应在类型检查中报错。阶段外、错误应答方和缺少必需数据的操作在写入前拒绝。查询合法动作使用同一套判定，可从只读局面预演；正式提交才记入骰序、回执和盘面。现存的全局待决顺序先按瓶中蝎回归保留，增加战役应答时单独核对中断点和返回点。

## 3. 规则记录怎样随代码维护

新增或修改机制时，在对应规则梳理和任务中保留三类独立记录。

| 记录 | 最小字段 |
| --- | --- |
| 原文 | 作品、版本、条款、页码、摘要、适用剧本、节 / 环 / 块、谁 / 何时 / 做什么 / 在哪里 |
| 实现 | 命令名、判定和结算入口、更新的状态、触发及应答方、回归用例 |
| 用户裁定 | 对应条款、原文疑点或来源冲突、裁定内容、适用范围、对应测试 |

例如，战役整理阶段自动改轨可追溯到 TTW 1.2 和用户 Q01。原文记录改轨规则，裁定记录采用整理阶段开始时的快照，实现记录 `ttw/campaign/rail.ts` 的规则函数、后续接入的阶段入口，以及验证同一整理阶段不连锁改轨的用例。缺少表、实体份数或原文解释时，在对应条目列出待核来源和受影响的动作。

## 4. 分批接入与验收

| 顺序 | 工作 | 验收 |
| --- | --- | --- |
| 已做 | 将后勤、地面战斗、空军任务和射击按机制接到统一会话。由规则模块提供当前空军和射击应答的窗口与行动方 | 模块边界与类型检查通过。固定种子瓶中蝎整局保持原结局。机场轰炸用例覆盖返航和守方容量应答相继打开 |
| 已做 | 建立战役地图格号及接缝索引，审计第聂伯河之战的初设、增援和胜利条件输入 | [全景剧本数据装配核对](2026-11-21-全景剧本数据装配核对.md) |
| 下一批 | 核对全景地图格边、初设标记、增援文本与胜利数据。另核普通运输点实体副本、战斗单位拆分表和池 | 缺项按来源确认后逐块装配到对局 |
| 全景剧本骨架 | 装配 A–D 战役地图和对应剧本数据，接通天气、先手、部署、阶段、增援、胜利判定。以实库连接战役移动、铁路、抽象与具象补给 | 能从真实初设开始，完成双方一个完整回合并进入下一回合，查验各段状态。瓶中蝎继续使用自己的小地图和剧本配置 |
| 全景完整规则 | 按阶段分批接入 KG、RVGK、特殊 HQ、STE、替换、撤编和事件等，一项从触发到完成做闭环 | 开发期间逐项验证合法、拒绝和中断恢复路径。全景终局验收由用户在最终阶段统一安排 |

开发期间执行相关类型检查、单项规则用例和数据核对。全剧本测试由用户在最终阶段统一安排。全景的性能验收使用 A–D 地图实际单位数和拓扑。面向玩家的存档在全景剧本可运行后再安排。
