# 瓶中蝎桌面 UI 接口

本文件对应 `protocolVersion: 1`。正式桌面 UI 可复用现有控制器和规则提交入口。当前 Windows 窗口通过本机子进程的标准输入输出交换逐行 JSON。

## 连接与操作

启动时由 [start.mjs](../desktop/local/start.mjs) 提供初始模型，包含底图、辅助卡、标定盒和初始 `local` 视图。窗口可发送 `{"kind":"ready"}` 获取最新视图，也可随时发送 `{"kind":"view"}`。同进程界面可调用 [controller.mjs](../desktop/local/controller.mjs) 的 `openLocalScorpion(data, savePath, seed?)`，再通过 `projectLocalScorpion(await controller.dispatch(request))` 取得同一视图。退出时调用 `close()`。

每次等待上一个请求返回后再发下一个。除 `ready`、`view` 外，请求均携带最新视图的 `revision`。保存并确认规则命令后修订号增加，点选、打开菜单和编辑草稿可产生同一修订号的新视图。界面每次用返回视图替换当前内容，包括同一修订号内更新的按钮和选区。

| 请求 `kind` | 附加字段 | 用途 |
| --- | --- | --- |
| `view` | 无 | 读取当前可显示状态。 |
| `board-left` | `x,y` 或 `cell`，可带 `unitId`、`confirm` | 点地图格、校准盒或其间的算子。逐枚点算子切换选中，同一枚再点一次取消。普通地面移动在点出路线后以 `confirm: true` 确认终点，也可选择侧栏操作。 |
| `select-unit` | `unitId`，整备时可带 `base` | 从名单点选或取消一枚算子。机场选择使用 `{kind:"hex",hex}` 或 `{kind:"off-map-air"}`。 |
| `board-menu` / `counter-menu` | 分别为地图坐标或盒编号，可带 `unitId`；或仅 `unitId` | 右键查询复杂操作，返回 `menu`。 |
| `aid-left` | `counterId` | 点击有操作入口的辅助卡算子。用返回的 `aidTargets` 引导地图选择，再用 `apply` 确认。 |
| `apply` | `key` | 提交当前 `actions` 或刚打开的 `menu` 中的一项。 |
| `clear-selection` | 无 | 清除选中项和当前草稿。 |
| `command` | `action` | 本机高级入口，提交一条 `ScorpionAction`。 |

成功响应为 `{"ok":true,"view":{...}}`，失败响应为 `{"ok":false,"error":"..."}`。因修订号或选项过期失败时，重新读取视图并重新选择。每个 `key` 都是当前视图生成的临时值。菜单只在刚打开时有效，界面应在后续操作前关闭旧菜单。按钮和菜单项提供 `label`、`kind`、`actionTypes`，部分项提供 `group`、`mapUnit` 或 `mapHex`。用 `kind: "draft"` 表示更新战果草稿，用 `kind: "command"` 表示提交规则命令。中文文案用于显示，业务分支使用英文字段值。

## 局面与坐标

| 字段 | UI 用法 |
| --- | --- |
| `revision`, `phaseId`, `turnNumber`, `phasingSide`, `actor`, `ended` | `phaseId` 是阶段标识。值为 `setup`、`initiative`、`aircraft-refit`、`reinforcement`、`movement`、`supply`、`reaction`、`combat`、`exploitation`、`cleanup` 或 `ended`。`actor` 是当前需要操作的一方，在反应、战斗和拦截时可能与 `phasingSide` 不同。 |
| `headline`, `phase`, `combatPrompt`, `aidPrompt`, `captureNotice` | 显示阶段和当前应答提示。 |
| `roster`, `stack`, `unitIds`, `unitId`, `hex`, `route` | 名单、打开的堆叠、已选单位、主选单位、目标格和路线草稿。用算子实例 ID 识别同型号单位。 |
| `stacking[]` | 当前行动方可处理的超堆叠格。每项含 `hex`、`re`、`limit` 和 `candidates: [{unitId,re}]`。移动阶段仍可移走单位。玩家也可选中同格算子，满足上限后由规则提交 `{type:"settle-stacking",hex,unitIds}`。 |
| `refit`, `supplyLines` | 飞机整备草稿、费用来源与抽象和具象补给提示。确认使用当前返回的操作。 |
| `transportStock[]` | 当前行动方的普通运输点库存行。每行包含 `side`、`mobility`（`truck` 为卡车，`leg` 为马车）、`allowance`、`points`、`inUse` 和 `limit`。已翻作延补队的算子仍计入原面额的 `inUse`。`limit: null` 表示实体副本数待核，可显示使用数和待核提示。 |
| `frame.mapStacks`, `frame.selectedUnits`, `frame.targets`, `frame.route`, `frame.retreatPaths` | 六角格中心、算子分布与分页、地图高亮和路线。状态标记用算子的 `badges` 小图或文字显示。 |
| `frame.trackers`, `frame.inventories`, `frame.auxiliaryCards`, `frame.aidCounters` | 小地图轨道、库存盒、独立辅助卡和苏军专用卡上的当前内容。隐藏的库存带 `hidden: true`。 |

地图和辅助卡都有独立的原图像素坐标。用启动模型里的尺寸和标定矩形绘制底图与盒，把平移和缩放的逆变换应用到鼠标坐标，再发送 `board-left` 或 `board-menu`。地图算子以 `mapStacks` 返回的格中心为锚，同格算子使用 `pages` 提供的偏移和分页。地图格 ID 如 `s10.02`，盒编号是布局中的 `cell`，辅助卡编号是 `cards[].id`。

## 辅助卡与对局联动

- 回合、天气、飞行条件、胜利分和死人堆随规则结算刷新。画小地图记录条时使用 `trackers[].cell` 定位标定盒。画独立辅助卡时用卡 ID 查找 `auxiliaryCards[cardId]`，其算子用返回的 `x,y,size` 定位。
- 预备标记按同方同格堆叠计数。提交 `mark-reserve`、`leave-reserve` 或 `release-reserve` 后，按新视图同时更新地图标记、辅助卡数量及剩余算子。混乱结算会释放该处清除的预备标记。
- Kessel HQ 放置从盒内 `counterId` 开始，点击合法格再确认。部署后按地图算子重绘。撤下或损失后的返回日期由规则层投影到回合天气卡，到期后回到可用盒。
- Kessel HQ 免费移动命令为 `{type:"kessel-move",unitId,headquartersId,path}`。两个 ID 都是图上算子实例 ID。左键点选一枚单位并逐格选路，右键终点选择提供支援的 HQ。也可直接右键相邻目标格。引擎读取起点并检查整条路线。
- 机场工程命令为 `{type:"work-airfield",operation,hex,unitIds,payments}`。操作值是 `build`、`build-strip` 或 `reduce`。左键选中工程单位后右键目标格，或直接右键该单位处理所在格。菜单列出可用操作和花费，缴费项使用 `{dumpId,tokens}`。跑道使用同一算子 ID 在 `frame.mapStacks` 与轴心离图卡的库存间切换。降级导致激活机超限时，现有应答流程接手。
- 运输点右键菜单中，`actionTypes` 含 `repack-transport` 的项同时提供 `transportOrder: {unitIds,divisions,continueWith}`。每个 `divisions` 元素含面额 `points` 和装载补给 `tokens`。`continueWith` 是继续移动的新算子在 `divisions` 中从零开始的序号，值为 `null` 时该方案无继续移动选项。提交时沿用菜单项的 `key`，由引擎重新校验。
- 带 `reference: true` 的卡目前供查看。KG 和分拆池等操作要等相应规则提供命令、合法目标和状态投影后再开放。

## 联网适配

正式界面可复用上述交互形态。当前本机桥接服务单机双方共用一个窗口，行动身份随 `actor` 切换。联网时由服务端根据登录席位调用 [submitScorpionSession](../src/match/scorpion-session.ts)，命令信封是 `{id,expectedRevision,action}`。服务端需按席位分别生成可见局面，串行提交并保存对局记录，随后回执。重复请求沿用原命令 ID，修订号冲突后重新同步。相关提交与回执语义见 [command-log.ts](../../../packages/match-core/src/command-log.ts)。
