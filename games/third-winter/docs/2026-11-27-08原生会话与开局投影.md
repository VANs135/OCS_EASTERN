## 0 结论

- 08 开局（印刷初设 → Alert 抽取 → 双方部署 → 进入首回合飞机整备）现在由 GDScript 会话结算并投影，TypeScript 只作为对照 oracle。

- 未覆盖：增援与之后的全部阶段。`place-arrival` 等需要补给网络、油费账本和增援日程，尚未移植。
- 盒区清单（`frame.inventories`）、回合轨（`frame.trackers`）、辅助卡（`frame.auxiliaryCards`）、苏军辅助卡炮击标记（`frame.aidCounters`）已由 GDScript 投影，逐步对照通过。
- `transportStock`（印刷运输面额与在盘计数）与 `breakdownStock`（拆分副本与可用 id）也已原生投影，08 开局视图现在与 TS 全量对照。

数值比较带 1e-6 容差并忽略整数/浮点差异；缺失键与 `null` 等价，与 `JSON.stringify` 丢弃 `undefined` 的语义一致。投影按行动方视角生成：对手的地图外空军盒隐藏，与桌面控制器一致。

## 4 与 TypeScript 的已知差异

- 会话未持久化：没有存档写入、没有数据指纹校验、没有续档恢复。
- `select-unit` 只实现开局语义（单枚选取）；对局阶段的空地分组、整备批次、同格翻页选择未迁。
- `board-menu` 返回空菜单；开局没有分组菜单行，真实入口在 `actions`。
- 没有分页算子、盒内清单与辅助卡绘制，`map_view.gd` 目前只消费已投影字段，因此接原生时不会崩溃，但界面上少这些面板。
- 运输面额只在兵种为 `transport`、非 `organic_truck`、非 `track`、印面 `transport` 为正整数时计入；`organicTruck` 在盘算子上是装载标记字符串（如 `full`），按“非空即排除”处理。
- 08 数据包的 `view.breakdownRows` 为空：本剧本没有拆分定义，函数保留生成 `availableIds` 的通路，等有副本数的剧本再验。
- `complete-refit` 只实现了无解冻的常规路径（08 首回合封冻）。解冻同步阶段、`settle-stacking` 减损路径与 `withScorpionPhaseOccupancy` 未迁。
- 对局阶段没有视图：`project()` 对非 `setup` 返回空字典，原生桥继续报“原生会话已超出 08 开局阶段”，这是刻意保留的边界。

## 7 自审与修正

对已迁模块逐条对回 TS 源码，找到并修掉两处真实语义偏差：

1. **运输面额按盘上字段分桶（已修）**。原实现拿部署算子的 `mobility`/`allowance` 去匹配面额行，而 TS 的 `printedDenomination` 只读**印刷**值。08 苏军 3 枚普通运输点（面额 2、2、1）在开局不暴露，改成苏军视角才看得出；一旦将来换面、延补队或拆分改了盘上字段，计数会错桶。现在数据包为每个定义导出 `moveProfile`（战斗面印刷 mobility/allowance），`transport_stock` 只按印刷口径计数。新增回归：把一枚普通运输点的 `mobility`/`allowance` 改成假值后重算，行与计数必须不变（此前会变）。
2. **阶段推进丢 cursor 附加字段（已修）**。原 `advance` 重新拼 cursor 字典，只留 `turn/first/phasing/phase/retention`，会丢掉解冻期的 `simulcast`。改为 `duplicate` 后只改相位字段，与 TS 的 `{ ...current, ...next }` 一致。

复核后确认一致、无需改动的点：

- `projects_zoc` 与 `projectsZoc` + `keepsCombatZoc` 的组合等价：攻方能、战斗面、未断补、非预备/混乱。
- 控制点查值顺序（`railControl` → 占领的战斗算子 → 开局战线）与 `scorpionControlLookup` 一致；只有印刷控制点有控制者。
- 固定补给 `sp × 4` 的整数算术、堆叠 `printedRe - stepsLost` 的取整、集合排序的 ASCII 口径（JS 默认 sort 与 GDScript 字符串排序一致）均与 TS 相符。
- 三参数无头 **808/808**：两参数 802 项之上新增“苏军面额有在盘计数”与“盘上字段漂移不影响计数”两项。

仍未对齐、按现状记录的边界：

- `breakdown_stock` 没有 `breakdownReturns`（回池身份复用）通路；08 无拆分定义，未暴露。
- `stacking.gd` 没有解冻期豁免集（`scorpionThawEntryHexes`）。
- `zoc_affects` 对未知动作返回“可抵消”而非抛错；当前调用点只有已知动作。

## 8 地形取费（本轮新增）

补给 trace 的前置是“走一格的代价”，也就是 TTW TEC 加 OCS 6.1d/6.2 的格边选择。本轮把这一层完整迁到 GDScript，并用 TS 的全边矩阵验收。

- `scripts/rules/series/ground_terrain.gd` 对应 `packages/series/src/ground-terrain.ts`：`most_expensive`（任一地形不可通则整格不可通，`all` 压过数字）与 `select_cost`（有可用路线就只取路线最小值，否则格值 + 格边值）。
- `works/third-winter/rules/terrain_cost.gd` 对应 `src/ttw/ground-terrain.ts` 与 `src/ttw/scorpion/terrain-cost.ts`：TEC 三列（Track/Truck/Leg）的 dry/freeze/mud 表、次要/主要河流的格边值、路线取费（道路 0.5、轨道/铁路 1，泥地卡车另计）、`ground_cell_cost`、`ordinary_terrain_cost`、`step_cost`、`trace_step_cost`。
- `step_cost` 的门槛照原实现：无格边即 null；有桥或有路且非河流才允许用路线；路线不可用时先查出发格的地形，出发格不可通就直接 null。
- `trace_step_cost` 的封冻口径是取 dry 与 freeze 的较小值，只有两边都是数值才比较——`all` 与 null 保持原值，不参与取小。
- 数据包新增 `view.mapGraph.terrains`（374 格的印刷地形），与已有的 `edges`/`neighbors` 一起构成原生取费所需的完整地图。
- 对照夹具 `scripts/godot-scorpion-terrain.mjs` 输出 `dist/godot/08-terrain.json`：1045 条印刷边、双向、三种机动、封冻/解冻两候，共 **12540** 条 trace 取费；另出 **6270** 条干地单列取费。

## 11 增援板（13.6 落点）

`works/third-winter/rules/reinforcement_board.gd` 只回答“这条抵达/这枚 Alert 能落在哪些格”，不落子、不记账：

- `occupancy(graph, ...)` 收集阻挡占位（敌方算子、敌方补给堆、双方印刷源、敌方机场）、Kessel 格集合、机场格、双方 `hasTrace` 集合；
- `arrival_destinations` 按 13.6：印刷落点里去掉被阻挡格；若整组落点全被挡且都在地图边缘，就用 13.6b 的边缘替代（与印刷边缘同一侧、未被阻挡、无 trace 要求），否则返回空；

## 31 正规战斗七步状态机

新增四个模块，按 OCS v4.3 §9.5–9.13 把正规战斗拆成七步：

- `godot/works/third-winter/rules/combat.gd`——状态机：`declare` / `defend` / `select_rating` / `choose_terrain` / `pending_decision` / `decision`。七步依次是守方补给 → 攻方选行动值 → 守方选行动值 → 守方选地形 → 攻方结算 → 守方结算 → 进击。
- `combat_supply.gd`——`attack_with_supply` / `defend_with_supply` / `defensive_supply_cost` / `total_tokens`：攻方宣告时按存活步数付战斗补给；守方按整堆口径付盘上补给或消耗自身内部库存，未付补给时防御强度下降。
- `combat_losses.gd`——`remaining` / `validate_loss_order` / `apply_losses`：结果码解析出双方强制与选项损失，行动值单位先承受第一点，逐轮均摊；落地走 `step_loss`，残部与 Kessel 只写待决占位。
- `combat_result.gd`——`roll_combat` / `resolve` / `advance`：选地形后按 2d6 + 攻方 AR − 守方 AR − 刺猬等级取 CRT；结算后符合条件的攻方单位得进击标记，守方被打穿时存活攻方进入目标格。

**验证**：夹具 `scripts/godot-combat.mjs` 6 场景 43 步——组合 A 五个变体（normal / hedgehog / 守方内部库存 / 守方未付 / 攻方断补）掷骰 `AL2`、攻方 2 点损失被消灭；组合 B 结果 `Ao1 DL1o1`，守方消灭进死人堆、存活攻方进击到 s2.10。用例 `godot/tests/cases/combat_cases.gd`。六参数 **2577/2577**、两参数 **2549/2549**（+350），`npm run check` 629/629。

## 32 本轮共同口径与偏差

- **UI 分层**：`tests/runner.gd` 的视图对照只比 `actions`（`label` + `actionTypes`）与 `frame` 九切片，**`menu` 不参与比对**。因此“新命令的可执行入口”只能落在 `menu` 层；凡在 TS 里出现在 `actions` 而原生只放进 `menu` 的项，都算一处 UI 偏差，逐项记在接线切片（第 33 节）里。
- **炮击观察者**：见第 29 节，任务描述里的“无观察者应拒”是我方描述错误，实现按 TS 不强制。
- **数据包即契约**：`view.faces` 里 `move` 为 `null` 的 15 条算子，任何换面/预备代码都必须显式判空，不得回退到合并数值。
- **不伪造**：所有未移植机制一律返回带错误码的 `Result.failure`，宁可让界面显示“不可执行”，也不做近似结算。

## 33 残部生成（TTW 2.4d）

第 25 节的 `rebuild` 只解决了“残部换回母单位”，生成这一半在战斗战损里补上了。

- **`remnants.gd` 新增 `place`**（`place_remnant` 为 TS 同名别名）：`place(state, division_id, division, requested, data)`，成功返回 `{ state, placed, remnantId, hex }`，`placed=false` 表示不合格、状态原样返回；失败码 `remnant_ineligible`（无残部算子却被指定落点）、`remnant_choice`（落点不在候选格）、`remnant_counter`（缺残部算子模板）。
- **合格师**：`Ge ` 前缀、步兵、RE 4，战斗面 16-AR 4-MA 3；**残部算子**从 `3999`/`4499` 里取首个不在盘面上的定义，id 形如 `remnant:land:id:3999`，`remnantOf` 指向母单位。**落点**：距母师 2 格、列号向西、按 `leg` 取费可抵达，排除苏军占领格与苏军补给源格，敌方 ZOC 格需有本方战斗单位压制，落点堆叠 `friendlyRe + 1 ≤ 10`。**继承**：`disorganized`/`reserve`/`exploit`/`exploitRating`/`released`/`outOfSupply`/`internalStocks` 逐字段拷自母单位，`moved`/`airlifted` 继承、`spent` 取母单位值；控制格只记 axis。
- **`combat_losses.gd`**：`apply_losses` 的返回值由 `pendingRemnants` 占位改为真实 `remnants` 名单（`{divisionId, remnantId, hex}`），打光的合格轴心师当场生成残部；非师级、苏军单位仍按既有分流（警戒营回池、余者进死人堆）。**VP 口径对齐 TS**：断补轴心单位按损失步数计，未断补且实际生成残部的师记 1 VP，其余 +0（VP 在战损里计，`place` 本身不计）。
