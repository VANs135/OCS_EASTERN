## 0 结论

- 08 开局（印刷初设 → Alert 抽取 → 双方部署 → 进入首回合飞机整备）现在由 GDScript 会话结算并投影，TypeScript 只作为对照 oracle。

- 未覆盖：增援与之后的全部阶段。`place-arrival` 等需要补给网络、油费账本和增援日程，尚未移植。
- 盒区清单（`frame.inventories`）、回合轨（`frame.trackers`）、辅助卡（`frame.auxiliaryCards`）、苏军辅助卡炮击标记（`frame.aidCounters`）已由 GDScript 投影，逐步对照通过。
- `transportStock`（印刷运输面额与在盘计数）与 `breakdownStock`（拆分副本与可用 id）也已原生投影，08 开局视图现在与 TS 全量对照。

数值比较带 1e-6 容差并忽略整数/浮点差异；缺失键与 `null` 等价，与 `JSON.stringify` 丢弃 `undefined` 的语义一致。投影按行动方视角生成：对手的地图外空军盒隐藏，与桌面控制器一致。

## 4 与 TypeScript 的已知差异

- 会话未持久化：没有存档写入、没有数据指纹校验、没有续档恢复。
- `select-unit` 只实现开局语义（单枚选取）；对局阶段的空地分组、整备批次、同格翻页选择未迁。
- `board-menu` 返回空菜单；开局没有分组菜单行，真实入口在 `actions`。
- 没有分页算子、盒内清单与辅助卡绘制，`map_view.gd` 目前只消费已投影字段，因此接原生时不会崩溃，但界面上少这些面板。
- 运输面额只在兵种为 `transport`、非 `organic_truck`、非 `track`、印面 `transport` 为正整数时计入；`organicTruck` 在盘算子上是装载标记字符串（如 `full`），按“非空即排除”处理。
- 08 数据包的 `view.breakdownRows` 为空：本剧本没有拆分定义，函数保留生成 `availableIds` 的通路，等有副本数的剧本再验。
- `complete-refit` 只实现了无解冻的常规路径（08 首回合封冻）。解冻同步阶段、`settle-stacking` 减损路径与 `withScorpionPhaseOccupancy` 未迁。
- 对局阶段没有视图：`project()` 对非 `setup` 返回空字典，原生桥继续报“原生会话已超出 08 开局阶段”，这是刻意保留的边界。

## 7 自审与修正

对已迁模块逐条对回 TS 源码，找到并修掉两处真实语义偏差：

1. **运输面额按盘上字段分桶（已修）**。原实现拿部署算子的 `mobility`/`allowance` 去匹配面额行，而 TS 的 `printedDenomination` 只读**印刷**值。08 苏军 3 枚普通运输点（面额 2、2、1）在开局不暴露，改成苏军视角才看得出；一旦将来换面、延补队或拆分改了盘上字段，计数会错桶。现在数据包为每个定义导出 `moveProfile`（战斗面印刷 mobility/allowance），`transport_stock` 只按印刷口径计数。新增回归：把一枚普通运输点的 `mobility`/`allowance` 改成假值后重算，行与计数必须不变（此前会变）。
2. **阶段推进丢 cursor 附加字段（已修）**。原 `advance` 重新拼 cursor 字典，只留 `turn/first/phasing/phase/retention`，会丢掉解冻期的 `simulcast`。改为 `duplicate` 后只改相位字段，与 TS 的 `{ ...current, ...next }` 一致。

复核后确认一致、无需改动的点：

- `projects_zoc` 与 `projectsZoc` + `keepsCombatZoc` 的组合等价：攻方能、战斗面、未断补、非预备/混乱。
- 控制点查值顺序（`railControl` → 占领的战斗算子 → 开局战线）与 `scorpionControlLookup` 一致；只有印刷控制点有控制者。
- 固定补给 `sp × 4` 的整数算术、堆叠 `printedRe - stepsLost` 的取整、集合排序的 ASCII 口径（JS 默认 sort 与 GDScript 字符串排序一致）均与 TS 相符。
- 三参数无头 **808/808**：两参数 802 项之上新增“苏军面额有在盘计数”与“盘上字段漂移不影响计数”两项。

仍未对齐、按现状记录的边界：

- `breakdown_stock` 没有 `breakdownReturns`（回池身份复用）通路；08 无拆分定义，未暴露。
- `stacking.gd` 没有解冻期豁免集（`scorpionThawEntryHexes`）。
- `zoc_affects` 对未知动作返回“可抵消”而非抛错；当前调用点只有已知动作。

## 8 地形取费（本轮新增）

补给 trace 的前置是“走一格的代价”，也就是 TTW TEC 加 OCS 6.1d/6.2 的格边选择。本轮把这一层完整迁到 GDScript，并用 TS 的全边矩阵验收。

- `scripts/rules/series/ground_terrain.gd` 对应 `packages/series/src/ground-terrain.ts`：`most_expensive`（任一地形不可通则整格不可通，`all` 压过数字）与 `select_cost`（有可用路线就只取路线最小值，否则格值 + 格边值）。
- `works/third-winter/rules/terrain_cost.gd` 对应 `src/ttw/ground-terrain.ts` 与 `src/ttw/scorpion/terrain-cost.ts`：TEC 三列（Track/Truck/Leg）的 dry/freeze/mud 表、次要/主要河流的格边值、路线取费（道路 0.5、轨道/铁路 1，泥地卡车另计）、`ground_cell_cost`、`ordinary_terrain_cost`、`step_cost`、`trace_step_cost`。
- `step_cost` 的门槛照原实现：无格边即 null；有桥或有路且非河流才允许用路线；路线不可用时先查出发格的地形，出发格不可通就直接 null。
- `trace_step_cost` 的封冻口径是取 dry 与 freeze 的较小值，只有两边都是数值才比较——`all` 与 null 保持原值，不参与取小。
- 数据包新增 `view.mapGraph.terrains`（374 格的印刷地形），与已有的 `edges`/`neighbors` 一起构成原生取费所需的完整地图。
- 对照夹具 `scripts/godot-scorpion-terrain.mjs` 输出 `dist/godot/08-terrain.json`：1045 条印刷边、双向、三种机动、封冻/解冻两候，共 **12540** 条 trace 取费；另出 **6270** 条干地单列取费。

## 11 增援板（13.6 落点）

`works/third-winter/rules/reinforcement_board.gd` 只回答“这条抵达/这枚 Alert 能落在哪些格”，不落子、不记账：

- `occupancy(graph, ...)` 收集阻挡占位（敌方算子、敌方补给堆、双方印刷源、敌方机场）、Kessel 格集合、机场格、双方 `hasTrace` 集合；
- `arrival_destinations` 按 13.6：印刷落点里去掉被阻挡格；若整组落点全被挡且都在地图边缘，就用 13.6b 的边缘替代（与印刷边缘同一侧、未被阻挡、无 trace 要求），否则返回空；

## 43 夺取窗口：默认手动，自动排序仅显式开启

`resolveScorpionEntry` 在 TS 里默认按 `captureResolution !== 'manual'` 自动排位移，只有夹具/测试显式传 `manual` 才挂窗口。但飞机落点、运输队分配、撤退路线这些都是玩家的选择（斯摩棱斯克的做法是把候选摆出来让玩家点，而不是替玩家挑），兵棋里不能把这类选择自动掉。所以原生把默认翻过来：

- `Capture.resolve_entry(..., manual := true)`：默认挂窗口，等玩家提交 `settle-capture`；只有调用方显式传 `manual=false` 才走自动排序。
- `automatic_order(capture, state, data, route)` 仍保留：危险度 = 2×（夺取方战斗算子所在格）+ 1×（仍在剩余路线上的格），飞机取「危险 0、最近、id 最小」的本方基地，否则 `off-map-air`；运输队取射程内同优先级一格，成员按 id 字典序分配 `takenPoints/takenTokens`，有剩则 `displacedTo`。它的用途是 AI/夹具的对照口径，不是玩家默认路径。
- 移动进格（`ground_move`）、战斗推进（`combat_result`）、撤退续跑（`retreat`）现在都保持挂窗口；这也回到此前 08 夹具验证过的行为。

**oracle**：`godot-capture.mjs` 每个场景记 `side` 与 `policy`，新增 `airbase-flip-auto`（6 枚停机飞机全部落 `off-map-air`）与 `transports-auto`（按 id 分配、余量自动位移）两个显式 auto 场景，8 场景 9 步；`capture_cases` 只有 `policy` 为 `auto` 的场景才传非手动。这样自动排序有 TS 对照，玩家路径保持手动。

## 44 夺取窗口的侧栏结算入口（临时简化版）

夺取窗口默认手动后，面板必须能给玩家一条出路，否则夺到飞机/运输队就卡死。按「UI 先简单、后面再设计」的要求，这一轮只做最小可用入口：

- `scorpion_view.menu_entries` 顶部判断：`state.capture != null` 时**只**调 `_append_capture_menu` 并直接返回，其它菜单一律不列（会话层的 `capture_pending` 守卫本来就拒其它命令，面板不再给出点了必被拒的行）。

- `automatic_order` 报错（例如没有可位移格）时给「需人工分配（面板待设计）」的占位行，不给可提交载荷——不猜数值。

**验证**：新用例 `capture_menu_cases.gd` 用 08 夹具 `airbase-flip` 手动窗口：原属方（轴心）面板只有一项、载荷是 `settle-capture`、经会话提交后窗口清空；非原属方只有等待提示且无载荷。六参数 **2981/2981**、两参数 **2953/2953**，`check:boundaries`、629/629 全绿。

**下一步**：正式选点面板（每枚飞机一个落点下拉、每支运输队一个夺取/位移选择、带预览），以及 `settle-capture` 的 Extender 分支；当前临时行只覆盖「接受候选顺序」这一种提交方式。
## 45 夺取归属即时结算，窗口只留真实位移选择

进格夺取分三件事：改控制/换机场/拿补给/削工事（**必然发生**）、掷骰决定运输队夺取量（**必然发生**）、以及飞机落点与运输队余量往哪放（**玩家选择**）。第 43 节把整坨都放进窗口，等于让玩家确认「必然发生」的部分；这一节把两者拆开：

- `resolve_entry` 的 `policy` 改三态：`player`（默认）、`manual`（TS 手动夹具口径，只要出现窗口就挂起）、`auto`（AI/夹具，一律自动排序结清）。
- `player` 下先看 `Capture.needs_choice(capture)`：没有运输队/延补队、且每枚飞机只有一个合法落点 → 窗口没有真正可选项，**直接按 automatic_order 结清**，面板不弹、玩家不被打断；出现多落点或运输队分配时才挂窗口。
- 归属改属本身发生在 `resolve_entry` 前半段：机场翻面、补给堆按骰转移、工事降级、控制记录都在窗口建立之前完成。窗口只带位移数据（`capture.aircraft` 候选、`capture.transports` 分组），不再等玩家确认归属。
- 面板文案同步：原属方一行改为「安排夺取位移 <格> · 按候选顺序填好（N 枚飞机、M 支运输队）」，非原属方为「等待<方>安排夺取位移」，`group` 从「夺取」改为「位移」。

**用例**：`capture_menu_cases.gd` 新增——进格后机场已翻给夺取方（不等确认）；`needs_choice` 四组表口径（单落点飞机 false、多落点 true、运输队 true、延补队 true）；面板行文案与载荷；提交后窗口清空。六参数 **2986/2986**、两参数 **2958/2958**，`check:boundaries`、629/629、`check:godot-vectors` 全绿。

**仍待**：正式位移面板（逐枚飞机落点、逐支运输队夺取量/位移格）；Extender 崩塌位移仍显式拒绝；`manual` 与 `player` 的差别只用于夹具对照，正式玩局走 `player`。

## 46 单机多落点：夺取面板逐落点成行

第 45 节之后，只有「真正存在位移选择」时才会挂窗口；但窗口里仍只有一行「按候选顺序填好」——一旦某枚飞机有两个合法落点，这一行就替玩家把落点定了。本节把这种最常见的选择摊开：

- 条件收紧：无运输队、无延补队、每枚飞机至少有一个落点、且**恰好一枚飞机**有多个落点。此时按该机的每个落点各出一行「安置飞机 <尾号> → <落点>」，其余飞机沿用各自唯一落点。玩家点哪行，飞机就落哪格。
- 其余情形（多枚飞机各自多落点、有运输队、有延补队）保留一行「按候选顺序填好」——那是 AI/夹具口径，正式面板待用户设计 UI 后替换。
- 落点标签：`kind=hex` 直接显示格子号，`off-map-air` 显示「地图外」。

**用例**：真实 08 夺取夹具里 6 枚飞机都只有 `off-map-air` 一个落点（`needs_choice` 为假，本来就不挂窗口），所以 `capture_menu_cases.gd` 用合成窗口验证：把首枚飞机的候选改成「夺取格 + 地图外」，断言行数等于候选数、每行载荷是 `settle-capture` 且只安置那一枚飞机；原有单行兜底与提交结清断言不变。

六参数 **2990/2990**（+4）、两参数 **2962/2962**（+4），`check:boundaries`、node 629/629、`check:godot-vectors` 全绿。

**仍待**：多枚飞机同时多落点与运输队逐项分配的正式面板；Extender 崩塌位移。

## 47 多机多落点：组合枚举（≤8 套）逐套成行

第 46 节只摊开「恰好一枚飞机多落点」；两枚以上各自多落点时仍退回一行「按候选顺序填好」，等于又替玩家选。本节把枚举推广到所有飞机：

## 49 批量加油两路（fuel-formation / fuel-headquarters）

- 数据投影：`setup.pools.breakdown` 是拆分池权威名单。生成器 `godot-scorpion-opening-data.mjs` 由池名解析定义并导出 `view.breakdownRows`（08 六条：轴心 `4008×3`、`4007×1`，苏军近卫 `2574×2`、`2575×2`，苏军普通 `1723×2`、`1724×2`）与 `view.breakdownParents`（43 个母单位到池的映射）。GDScript 不按名称反推池，父单位入池只读投影。
- 拆出：`detach-breakdown` 须在 `movement` 且本方 `phasing`、单位未 `moved`、未空运、未花活动点；候选须同池、库存有余、AR 不高于母单位；每次逐条选一枚。错误码 `breakdown_parent` / `breakdown_window` / `breakdown_pool` / `breakdown_count` / `breakdown_choice` / `breakdown_face`。
- 吸收：`complete-movement` 先检查 `Breakdown.obligations`；若有义务则建立会话级 `breakdownAbsorb` 窗口并阻塞其它命令，侧栏只列义务清单里的母单位与拆分单位。玩家逐条 `absorb-breakdown`，母单位恢复一步、拆分 ID 入 `breakdownReturns`，义务清空后窗口自动关闭。错误码 `breakdown_absorb_pending` / `breakdown_absorb_hex` / `breakdown_absorb_flags`。
- 库存按“全盘同定义已用数”扣减，吸收返还的 ID 优先复用。08 轴心池已有 6/3 枚同定义在盘、池 `copies` 为 3/1，按该口径轴心可用为 0；本切片测试用苏军近卫师，不修改数据可靠性。
- TS oracle 目前只有拆出（`scorpion-breakdowns.ts`），没有吸收实现；为让 `08-scorpion.json` 的视图含拆分行，正式库补 `scenarios/08-korsun-pocket/breakdowns.json`（父单位 43、计数器 6，来自 `setup.pools.breakdown`）。吸收窗口与 08 实库行为由 `breakdown_cases.gd` 单独覆盖，不进入 TS 对照。
- 测试 `breakdown_cases.gd` 覆盖 6 条拆分池/43 个母单位投影、AR 上限候选、开始移动拆出、连续拆两步、只剩最后一步拒绝、已移动拒绝、段末窗口、未吸收阻塞、并回返还 ID。未覆盖：战后推进/战后撤退窗口、与 Extender 崩塌位移。
- 门禁：六参数 **3179/3179**、两参数 **3151/3151**、node **629/629**、`check:boundaries` 与 `godot-core-vectors` 通过。
