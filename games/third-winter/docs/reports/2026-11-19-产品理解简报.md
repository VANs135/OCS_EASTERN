## 核心结论

**规则不是瓶颈，产品化才是。**

这个项目的规则内核已经跑通——TASKS.md「已通过核验」的 29 条全部勾选，我在本地装好依赖后重跑 130 项回归测试全绿、类型检查和依赖边界检查都通过。真正卡住的是 TASKS.md 里剩下的 11 条，其中 3 条直接决定「用什么客户端、怎么联机」。这三条不定，继续往下堆桌面交互随时可能作废。

接手第一件事不是接着写规则，而是**先定客户端形态**，同时把「本机资料库 + OCS v4.3 正版图表 PDF」这条硬前置补齐——否则新人在自己机器上连一局都跑不起来。

**一个必须先知道的坑：**克隆后直接跑测试会失败 14 项，报 `Cannot find package '@ocs-eastern/series'`。先 `npm ci` 再跑，全绿。这不是代码缺陷，但会让接手的人第一眼误判「项目跑不起来」。

## 要点速览

- **定位：**OCS v4.3 东线作品软件实现，首作《第三冬》、首剧本「瓶中蝎」。给两人对局的兵棋玩家，目标是「两名异地玩家在 Windows 安装版中完成初设、互相应答、断线续局和终局结算，并能用同一规则内核进行本地热座」（TASKS.md 首段）。
- **当前形态：**规则引擎 + 本地热座桌面端，但桌面端是 **Node 进程 + PowerShell 窗口的自测壳**（`start.mjs` 用 `spawn('powershell.exe')` 拉起 `CalibratedMap.ps1`），不是发布级客户端。TASKS.md 明确要求先试做 Tauri 与 Godot 原型再定客户端。
- **已实现：**空中作战是最完整的一块（整备、转场扫荡、对地/机场轰炸、低空扫射、运输破坏、补给空运、战斗单位空运、空投）；地面侧覆盖补给追溯、燃料三法、运输点与编内卡车、延补队、正规战斗、炮击、突袭、工事、残部营、重掷、解冻。全部可追溯到 README「当前覆盖」46 条的具体条号。
- **未完成 11 条：**规则与资料待接入 6 条、桌面交互 2 条、联网与安装包 3 条。每条都逐字引自 TASKS.md 并标注了所在小节与条序，可在文档里对回原文。
- **实测数字：**TS/mjs 159 个文件 14,363 行 + PowerShell 703 行；40 条提交集中在约 43 小时内（2026-11-17 11:28 至 11-19 06:14 UTC）；无 CI，回归靠手动 `npm run check`。

## 接手建议（按用户价值排序）

1. **先定客户端**（对应 TASKS.md〈桌面与互联网联机〉第 1 条）——唯一的「上游决定项」，后两条界面工作量的多少取决于它选谁；现有界面代码约 1,563 行加 703 行 PowerShell，属可丢弃的验证成本。
2. **补齐「新人能跑起来」的资料前置**——唯一阻断所有人的点，却不在那 11 条里。需要本机资料库和正版图表 PDF 第 3、4 页导出的三张表。
3. **建立规则裁定档**——README 有 6 处「按用户裁定」、TASKS.md 有 3 处（我检索统计 README「用户裁定」共 9 处），都是口头决定散落在长段里；且 README 引用的总体设计文档 `docs/2026-11-17-…研发方案.md` **不在仓库内**。
4. **权威裁判服务与持久化**（第 4 条）——规则已全通、命令本就带版本与去重，此时切入联机改的是传输层不是规则层，成本最低。
5. **Windows 安装包与双机演示**（第 5 条）——TASKS.md 自己写的验收目标，必须当发布门槛而不是收尾工作。

**本期建议不做：**战役扩展与多作品移植、战役专属规则（苏军特殊卡车延补队）、战役地图接缝核对——三者都依赖瓶中蝎首版验收，提前动会让「跑通一个剧本」失控成「跑通整场战役」。

## 需要你确认的一件事

README 引用的总体设计文档 `docs/2026-11-17-第三冬与后续OCS桌面游戏研发方案.md` 不在仓库里。这份文档决定了「Tauri 还是 Godot」这类选型的原始意图，建议向原作者索取后入库存档——否则客户端选型这一步只能从零重新论证。
